# Сверка условий договоров поставки — прототип

Локальное веб-приложение без зависимостей: загрузите TXT-файлы, получите таблицу «договор — поставщик — сумма — срок на дату проверки», где у каждого значения есть файл, точная цитата и переход к абзацу исходного текста.

## Запуск

Нужен только браузер. Для тестов — Node.js ≥ 18.

```bash
open index.html
```

(или любой статический сервер: `npm start` → http://localhost:8000)

Затем: «Выбрать файлы» (или перетащить) → выбрать все файлы из `documents/` → таблица строится сразу. Дата проверки по умолчанию 10.03.2026, её можно менять.

Тесты:

```bash
npm test
```

## Как пользоваться

1. Откройте `index.html`, перетащите файлы из `documents/` или нажмите «+ Добавить файлы». Можно загружать все сразу и в любом порядке; повторно загруженный файл с тем же именем заменяет прежний (удобно, если поменять поле в договоре).
2. **Реестр договоров**: номер, поставщик, сумма в рублях, срок поставки на дату проверки (по умолчанию 10.03.2026, можно менять). У каждого значения есть имя файла, номер абзаца и точная цитата. Нажатие на «📄 Источник» открывает документ справа, прокручивает его к абзацу и выделяет цитату.
3. Если значение изменено допсоглашением, рядом стоит метка «Изменено допсоглашением», зачёркнутое прежнее значение и ссылка «Было» на договор.
4. В колонке **«Не согласовано (не учтено)»** видны письма, проекты и ещё не вступившие в силу допсоглашения с предлагаемыми значениями и цитатами. В расчёт они не входят.
5. В колонке **«Статус проверки»** видно одно из трёх: «Всё подтверждено», «Есть несогласованные предложения» или «Требует проверки» с причиной (нет данных, неясен статус подписания, конфликт, дубль номера). Фильтр «Только требующие внимания» оставляет только проблемные строки.
6. **Быстрые вопросы**: четыре кнопки по вопросам из задания, плюс свой запрос («поле × договор» и «поставка раньше даты»). Номера договоров в кнопках взяты из формулировок вопросов; сами ответы вычисляются из загруженного текста.
7. **Загруженные документы**: как система распознала каждый файл (тип, номер договора, статус). Так видно, почему документ учтён или не учтён.

Ответы на тестовом наборе (дата 10.03.2026):

| Вопрос | Ответ | Основание |
|---|---|---|
| Срок STN-101 | 30.04.2026 | 02_amendment_signed.txt, п. 2 (было 15.04.2026 по 01_contract.txt); проект 06 предлагает 10.05.2026 — не учтён |
| Сумма STN-102 | 840 000 ₽ | 03_contract.txt, п. 2.1 (аванс 252 000 не считается суммой) |
| Сумма STN-103 | нет данных | 04_contract.txt, п. 2.1: стоимость по спецификации, которой нет; лимит 600 000 не является ценой |
| Поставка < 01.04.2026 | STN-102 (20.03.2026) | есть несогласованный перенос на 27.03.2026 — письмо 05_supplier_email.txt |

## Структура

```
index.html            UI: загрузка, таблица, вопросы, просмотр источника
src/parser.js         извлечение и правила статусов (браузер + Node)
documents/            исходные 6 файлов задания
tests/parser.test.js  16 тестов (node:test)
tests/fixtures/alt_format/  те же сценарии в другом оформлении (месяцы словами, «№», НДС в скобках)
```

## Известные ограничения

- Правила рассчитаны на русскоязычные договоры похожей структуры: ключевые фразы «общая стоимость / цена договора», «срок поставки / поставить … не позднее», «Статус:», «вступает в силу». Иная формулировка → «нет данных» или «требует проверки», а не выдуманное значение.
- Относительные сроки («в течение 30 дней после аванса») не вычисляются — показываются как «нет данных» с цитатой.
- В изменяющих документах берётся последнее значение в предложении; значение после «с … / вместо …» считается старым.
- Сумма — одна на договор; спецификации, партии, валюты кроме рубля не поддерживаются.
- Номер договора: заглавные буквы + цифры (`STN-101`, `АБ-12/3`).
- Только TXT в UTF-8; данные живут в памяти вкладки и никуда не отправляются.

# Записка (≤ 2 стр.)

**Пользователь.** Специалист по закупкам, сверяющий действующие сумму и срок по пачке договоров и сопутствующей переписке. Ему важна не скорость чтения, а уверенность: «значение откуда, и не перекрыто ли оно чем-то».

**Пять вопросов клиенту.**
1. Какие поля нужны помимо суммы и срока (неустойка, условия оплаты, спецификации/партии) и что делать с многопартийными поставками?
2. Откуда приходят документы (СЭД, почта, сканы) и где источник правды о подписании — текст, ЭЦП, отметка в СЭД?
3. Что пользователь делает с результатом: экспорт, задача юристу, напоминание о сроке? Кто исправляет ошибку извлечения?
4. Насколько вариативны шаблоны договоров у разных контрагентов, и есть ли свой шаблон компании?
5. Какая цена ошибки: лучше «нет данных» в 20 % случаев или ошибка в 1 %? (Прототип выбирает первое.)

**Допущения.** Условия меняет только допсоглашение со статусом «подписано обеими сторонами» и датой вступления в силу ≤ даты проверки. Тип и статус документа берутся из текста (заголовок, строка «Статус:»), а не из имени файла или порядка загрузки. При нескольких применимых допсоглашениях действует последнее по дате вступления в силу; одинаковая дата и разные значения → «требует проверки». Сумма — «общая/итоговая стоимость» или «цена/сумма договора»; аванс, лимит, бюджет, неустойка игнорируются; даты оплаты/приёмки не являются сроком поставки.

**Метрики.**
1. *Точность с основанием*: доля значений, где значение верно и цитата его действительно содержит (цель ≥ 98 %); отдельно — доля ложных значений там, где правильный ответ «нет данных» (цель 0).
2. *Время сверки договора*: от загрузки до подтверждённого значения против ручного чтения; плюс доля значений, которые пользователь открыл в источнике и не исправил.

**Архитектура.**

```
TXT ─► разбиение на абзацы/предложения ─► классификация (договор / допсоглашение / письмо)
     ─► статус (подписан / проект / неясно) + дата вступления в силу
     ─► извлечение полей (правило → значение + {файл, абзац, цитата})
     ─► связывание по номеру договора ─► применение подписанных и вступивших изменений
     ─► реестр + «несогласованные» + «требует проверки» ─► UI / ответы на вопросы
```

Всё выполняется в браузере (`src/parser.js` — чистые функции, тот же код гоняется в тестах Node).

**Почему правила, а не LLM, и где это перестаёт работать.** Задача требует точного значения с дословным основанием и запрета на выдумывание. Правила дают это по построению: значение всегда разобрано из найденного предложения, а при отсутствии совпадения ответ «нет данных». Подход надёжен для документов одного шаблона (типовые договоры компании, тот же «общий формат», что обещан на встрече). Он ломается на свободных формулировках, таблицах, сканах и сроках, заданных событием («через 10 дней после аванса»). Там нужна модель, но в роли поставщика кандидатов, а не источника истины (см. улучшение 2).

**Три решения и компромиссы.**
1. *Правила вместо LLM.* Детерминированно, бесплатно, офлайн, каждая цитата гарантированно из текста, легко тестировать. Цена — хрупкость к непривычным формулировкам; смягчено тем, что промах даёт «нет данных/проверить», а не значение. LLM разумно добавить позже как «кандидат-экстрактор» с обязательной проверкой, что цитата дословно есть в тексте.
2. *Атомарный источник = предложение внутри абзаца.* Цитата короткая и точная, переход к абзацу работает. Цена — предложения, разбитые иначе (сокращения «т.д.»), дают более длинную цитату.
3. *Без сервера.* Запуск одной командой, документы не покидают машину. Цена — нет хранения, истории, совместной работы; масштаб ограничен вкладкой.

**100 000 документов и права доступа.** Нужен бэкенд: очередь извлечения при загрузке, хранение документов и извлечённых фактов (Postgres: документ, факт, источник-офсет, версия правил), индекс по номеру договора и контрагенту, полнотекстовый поиск. Связывание — не только по номеру, но и по контрагенту/датам, с очередью ручного разбора. Права — на уровне договора/подразделения (RLS), фильтрация применяется и к фактам, и к цитатам; аудит просмотров. Пересчёт «на дату» — запросом по фактам, а не повторным парсингом. Мониторинг качества: доля «нет данных» по шаблонам контрагентов.

**Следующие улучшения (по приоритету).**
1. Ручное подтверждение/исправление значения пользователем с сохранением и метрикой ошибок по правилам.
2. Гибридный экстрактор: LLM (локальная, напр. через Ollama, или API) предлагает значение + цитату; приложение принимает только если цитата дословно найдена и значение из неё парсится правилом.
3. Новые поля (неустойка, условия оплаты) и спецификации/партии; экспорт реестра в XLSX.

# Отчёт о вайбкодинге

**Инструмент:** Claude Code (Opus) в десктоп-приложении Claude; парсер, UI, тесты и README написаны через него, проверка — `npm test` и прогон UI во встроенном браузере.

**Характерные запросы.**
1. Вставлен полный текст задания: «сделай прототип» — ИИ выбрал стек (vanilla JS без сборки, `node:test`), спроектировал модель «значение + источник + статус документа».
2. «Вот 6 реальных файлов» — переадаптация правил под их формат (строка «Статус:», «К ДОГОВОРУ STN-101» без «№», письмо с полями «От/Тема»).
3. Тесты на ловушки: аванс vs сумма, лимит бюджета vs цена, дата оплаты vs срок поставки, допсоглашение, вступающее в силу после даты проверки, новый договор того же формата.

**Ошибка ИИ и как поймана.** До получения реальных файлов ИИ сам сочинил учебные документы и написал регулярки с `\w`. На первом прогоне все суммы оказались `null`, а допсоглашения распознавались как договоры. Диагностика: вывод реестра в консоль → сумма пустая даже там, где число очевидно → в JS `\w` не матчит кириллицу (`стоимост\w*` не ловит «стоимость»). Исправлено заменой на `[а-яёa-z]`, закреплено тестами. Второй пример: первая версия брала поле из целой строки, и в STN-102 «аванс 252 000» и «оплата до 10.04.2026» стояли рядом с ключевыми словами; переход на уровень предложений + списки исключений (`аванс|лимит|бюджет…`, `оплат|приемк`), под каждую ловушку — отдельный тест.

**Затраты времени и что осталось.** Фактическое время: _заполнить_ (≈ __ ч из 4). Не сделано: ручное подтверждение значений; извлечение неустойки (планируемое изменение на встрече — по образцу `extractField` с новым ключом и `%`); e2e-тест UI (проверено вручную в браузере).
